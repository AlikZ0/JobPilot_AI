# Архитектура

JobPilot AI — расширение на Manifest V3 с четырьмя контекстами выполнения. Всё,
что они говорят друг другу, идёт через одно типизированное объединение
сообщений; строковых литералов в местах вызова нет.

```
┌──────────────┐  типизированные      ┌─────────────────────┐
│  Боковая     │  сообщения           │  Service worker     │
│  панель      │◀────────────────────▶│  (фон)              │
└──────┬───────┘                      └────────┬────────────┘
       │ прямое чтение Dexie                   │ chrome.scripting
       │ (быстро, в основном чтение)           │ + типизированные сообщения
       ▼                                       ▼
┌──────────────┐                      ┌─────────────────────┐
│  IndexedDB   │                      │  Content-скрипт     │
│  (Dexie)     │                      │  (по вкладке)       │
└──────────────┘                      └─────────────────────┘
```

- **Боковая панель** (`src/sidepanel`) — основной интерфейс. Для отрисовки она
  читает базу напрямую, а сообщения шлёт для всего, что касается вкладок и AI.
- **Service worker** (`src/background`) владеет автоматизацией вкладок, очередью
  анализа, горячими клавишами, уведомлениями и всеми вызовами AI. Это
  единственный контекст, который может прочитать API-ключ.
- **Content-скрипт** (`src/content`) внедряется по требованию. Он извлекает
  вакансии, читает формы и заполняет одобренные поля. Ключей он не видит и
  сетевых запросов не делает.
- **Попап** (`src/popup`) — лаунчер для двух самых частых действий.

## Шина сообщений

`src/types/messages.ts` определяет одно объединение `MessageDefs`. Каждый элемент
связывает константу типа с полезной нагрузкой и результатом:

```ts
type Def<T, P, R> = { type: T; payload: P; result: R };
```

`sendToBackground(type, payload)` и `sendToTab(tabId, type, payload)` выводят обе
стороны из этого объединения, а `registerMessageHandlers({...})` проверяет по нему
каждый обработчик. Ошибки пересекают границу как `SerializedError` со стабильным
кодом, поэтому интерфейс показывает конкретное сообщение, а не «что-то пошло не
так».

## Конвейер извлечения

`src/core/extraction/pipeline.ts` сливает четыре слоя по приоритету и записывает
источник каждого поля в `fieldSources`:

1. **JSON-LD** `JobPosting` (`jsonld.ts`) — самый надёжный, выигрывает по всем
   полям, которые в нём есть.
2. **Подсказки адаптера** — селекторы конкретного сайта.
3. **Meta-теги** (`meta.ts`) — Open Graph и родственные.
4. **DOM-эвристики** (`heuristics.ts`) — сначала подписанные селекторы, затем
   поиск самого «плотного» текста со штрафом за блоки с обилием ссылок.

Пятый слой — извлечение через AI — включается, только если результат слияния
непригоден, поэтому на нормальных страницах он ничего не стоит.

`computeQuality()` превращает происхождение и полноту в число от 0 до 1, которое
видно в интерфейсе, а `splitSections()` делит описание на требования, обязанности
и условия, ориентируясь на заголовки (с запасным вариантом по спискам).

## Скоринг

`src/core/scoring/engine.ts` — единственное место, где рождается процент.

0. Веса компонентов берутся из настроек и приводятся к сотне
   (`normalizeWeights()` в `weights.ts`): ползунки задают важность, а максимум
   балла обязан остаться ровно 100. Подпись весов (`weightsKey()`) уходит в
   анализ и входит в ключ кеша.
1. `matchSkills()` приводит обе стороны через словарь технологий
   (`techDictionary.ts`), который знает синонимы (`nodejs` → `Node.js`) и
   следствия (`Nuxt` → `Vue` → `JavaScript`), и делит технологии вакансии на
   обязательные и желательные по формулировке требований.
2. Выводы AI, если они есть, вливаются — но навык, который модель приписала
   пользователю, отбрасывается, если его нет в профиле.
3. Восемь функций-оценщиков возвращают `{ earned, max, detail }`.
4. Компоненты складываются и округляются; уровень берётся по фиксированным
   порогам.

Поскольку каждый оценщик — чистая функция от `(job, profile, findings)`, одни и
те же входные данные всегда дают одно и то же число, а разбор всегда сходится с
итогом. Оба свойства проверяются в `tests/unit/scoring.test.ts`.

## Конвейер анализа

`src/core/analysis/analyzeJob.ts`:

```
попадание в кеш? ──да──▶ переиспользуем (без вызова AI)
   │нет
   ▼
вакансия → analyzing → выводы AI (необязательно, сбой допустим) → детерминированный балл
   → сохранение анализа → вакансия → analyzed
```

Ключ кеша — `(jobFingerprint, profileVersion, ANALYSIS_VERSION, weightsKey)`. Правка профиля
увеличивает `profileVersion` и обесценивает весь кеш; при изменении движка
скоринга нужно увеличить `ANALYSIS_VERSION`. Смена весов приоритетов меняет
`weightsKey` и обесценивает кеш сама по себе; уже сохранённые баллы переписывает
`core/scoring/rescore.ts` — по кнопке в настройках и без обращения к AI: он берёт
качественную часть из сохранённых в анализе выводов модели.

## Массовый анализ

`src/background/scanController.ts` управляет агентом обхода вакансий:

1. Просит content-скрипт на странице списка отдать ссылки на вакансии.
2. Собирает `JobQueue` с параллельностью (1–3, жёсткий предел) и паузой между
   стартами задач.
3. Для каждой вакансии: открыть фоновую вкладку → дождаться загрузки → внедрить
   content-скрипт → извлечь → сохранить с дедупликацией → проанализировать →
   закрыть вкладку.
4. После каждого шага публикует `ScanProgress`, чтобы панель показывала живые
   счётчики; шлёт уведомления о высоких баллах и о завершении.

Пауза, продолжение и остановка кооперативные: `stop()` отменяет общий
`AbortSignal` и очищает очередь, а каждая открытая вкладка закрывается в блоке
`finally`.

## Резюме и ATS

`src/core/resume/` собран из пяти независимых частей:

- `pdfText.ts` — извлечение текста из PDF через pdf.js. Библиотека грузится
  динамически (отдельный чанк) и только когда пользователь импортирует файл;
  воркер берётся из бандла, `isEvalSupported: false`.
- `atsAudit.ts` — восемь детерминированных проверок формата: текстовый слой,
  контакты, разделы, даты, объём, колонки, символы, имя файла. Каждая
  непройденная проверка обязана объяснить, что исправить.
- `gapAnalysis.ts` — сравнение требований вакансии с профилем и текстом резюме;
  отсюда берётся деление на «есть в резюме», «есть у вас, но не написано» и
  «нет нигде».
- `matchVersions.ts` — какой из вариантов резюме ближе к конкретной вакансии.
  Считается тем же разбором пробелов: доля требований, про которые в тексте
  варианта действительно написано. Без AI — выбор версии должен быть объясним.
- `tailorResume.ts` — подгонка. Сначала считаются пробелы, затем модель
  переписывает текст, а `enforceTruthfulness()` выбрасывает из её ответа всё,
  что не подтверждено профилем или исходным резюме: и навыки, и выдуманных
  работодателей. Есть путь без AI — `tailorWithoutAI()`.

Вариантов резюме может быть несколько: под разные роли ищут по-разному, и одно
резюме на всё сразу проигрывает и там, и там. Вариант — это запись в `resumes`
с `jobId: null`, подогнанная копия ссылается на вакансию и на вариант, из
которого собрана. Записи из баз, не знавших о вариантах, дополняются при чтении
(`normalize` в `resumeRepository.ts`), а не миграцией — так база остаётся
читаемой и предыдущей версией расширения.

`render.ts` отрисовывает результат в простой текст, markdown и печатный HTML.
Мы намеренно не редактируем исходный PDF: надёжно переставить текст внутри чужой
вёрстки нельзя, а ATS в любом случае лучше читает чистый документ в одну колонку.

## Отчёт и экспорт

`src/core/pipeline/report.ts` — сводка за период, разбор по источникам, самые
частые требования и сериализация в CSV и Markdown. Всё по локальной базе и без
AI: цифры, которые человек кому-то показывает, должны быть проверяемыми.

Источник берётся из адреса вакансии, а не из поля `source`: там лежит
идентификатор адаптера, и все незнакомые сайты слились бы в один «generic».
Ступени воронки в недельной сводке считаются по датам их достижения — ответ мог
прийти на отклик, отправленный месяц назад, и относится он к этой неделе.

CSV пишется с BOM и разделителем «;» ради Excel в русской локали, экранирование
по RFC 4180. `Blob.text()` в браузере срезает BOM при декодировании — это
особенность спецификации, а не потеря: в байтах файла он есть.

## Разбор списка

`src/core/pipeline/triage.ts` — пометки, архив и скрытые компании. Всё чистыми
функциями: от того, что человек убрал компанию из выдачи, зависит, увидит ли он
вакансию вообще, и такое решение должно быть предсказуемым.

Сравнение пометок и названий компаний сделано отдельно от `normalizeToken`, хотя
тот и напрашивается: он собран под технологии и оставляет только латиницу с
цифрами. На нём любые две русские пометки схлопывались бы в пустую строку и
считались одинаковыми, а русское название компании нельзя было бы скрыть вовсе.
`normalizeCompany` для компаний по-прежнему используется — он убирает правовые
формы, — но если после него от названия ничего не осталось, сравниваются сами
названия.

Скрытые компании отсекаются в `store.refreshData`, а не на каждом экране: иначе
вакансия из чёрного списка всё равно попадала бы в счётчики обзора.

## Воронка откликов

`src/core/pipeline/funnel.ts` — чистые функции: какие отметки проставить при
переходе на ступень, как сложить воронку и у каких заявок подошёл срок
напоминания.

`ApplicationOutcome` — отдельная ось от `ApplicationState`. Та описывает
подготовку заявки (черновик → готова → отправлена), эта — ответ работодателя;
заявка бывает отправлена и без ответа, а отказ приходит на любой ступени.
Смешивать их в одном перечислении нельзя.

Воронка считается по отметкам `outcomeAt`, а не по текущему `outcome`: заявка,
дошедшая до интервью и получившая отказ, всё равно была ответом и была
интервью.

Напоминания живут на одном периодическом `chrome.alarms`
(`src/background/followUps.ts`). Будильник на заявку не заводится: воркер
засыпает и просыпается когда угодно, а Chrome хранит будильники сам — проще при
каждом срабатывании перечитать заявки, чем следить за жизнью десятков таймеров
и восстанавливать их после перезапуска. Срок снимается сразу после показа,
иначе следующий час показал бы то же уведомление снова.

## Машины состояний

В `src/core/state/` описаны разрешённые переходы для вакансий и заявок, и каждая
запись в репозиторий проходит через проверку. Отправить отклик человек может на
любом шаге подготовки — прямо на сайте, не доводя черновик до `ready`, — поэтому
переход в `submitted` разрешён из всех рабочих состояний, кроме отменённого. Из
`submitted` ведёт единственный путь назад: откат ошибочной автоматической
отметки в `ready`.

## Журнал откликов

Заявка (`applications`) описывает подготовку отклика внутри JobPilot и живёт по
строгому автомату. Но откликнуться можно и мимо расширения — прямо на сайте.
Поэтому факт «я откликнулся сюда тогда-то» хранится отдельно, в `submissions`.

Как запись туда попадает:

- `content/tracking.ts` замечает `submit` формы, похожей на форму отклика, текст
  вида «спасибо за отклик» или метку сайта «вы откликались»;
- `background/submissionTracker.ts` находит вакансию по URL (при необходимости
  дочитывает её со страницы), сохраняет снимок «должность + компания + балл» и
  схлопывает повторные сигналы по одной вакансии в пределах 12 часов;
- подтверждение на экране проверки (`markSubmitted`) пишет туда же, но с
  `source: 'manual'` — ручная запись никогда не понижается до автоматической.

Заодно заявка переводится в `submitted` через `markSubmittedAutomatically`
(настройка `automation.autoMarkSubmitted`, включена по умолчанию). Если черновика
заявки не было — он создаётся, чтобы отклик был виден и в списке заявок. Отметка
хранит `submissionSource: 'auto'` и откатывается одной кнопкой на экране
проверки; подтверждённая человеком — нет.

Пассивные функции работают только на сайтах с выданным доступом: content-скрипт
регистрируется динамически (`background/contentScripts.ts`) и снимается, когда
обе настройки выключены.

## Модель данных

Dexie (`src/database/db.ts`), десять хранилищ: profiles, settings, jobs, analyses,
applications, applicationEvents, submissions, aiUsage, assistantMessages,
scanSessions. Каждая запись валидируется Zod и на входе, и на выходе, поэтому
изменение схемы или отредактированный вручную импорт не могут сломать интерфейс.
