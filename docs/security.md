# Безопасность

## Модель угроз

JobPilot работает внутри страниц, которые ему не принадлежат, держит API-ключ и
хранит персональные данные. Три вещи, которые не должны случиться никогда:

1. Сайт вакансий получает API-ключ или профиль.
2. Текст со страницы или из модели выполняется как код.
3. Заявка отправляется без явного действия человека.

## Никакого удалённого кода

- Manifest V3 с `script-src 'self'; object-src 'self'`.
- Нет `eval`, `new Function`, внешних `<script>` и `innerHTML`.
- ESLint включает `no-eval`, `no-implied-eval`, `no-new-func`; юнит-тест
  (`tests/unit/security.test.ts`) проходит grep-ом по всему `src/` в поисках
  `eval(`, `new Function(`, `.innerHTML =` и `dangerouslySetInnerHTML` и валит
  сборку при находке.
- HTML из JSON-LD превращается в текст собственным декодером
  (`core/extraction/html.ts`), а не присваиванием в DOM-узел.

## Вывод AI — это данные

Каждый ответ проходит `parseAIJson()` → Zod. Непроверенный текст модели не
попадает ни в DOM, ни в селектор, ни в URL, ни в хранилище. Поля-перечисления
(коды красных флагов, типы полей, уровни) отклоняют неизвестные значения, а не
приводят их к чему-то.

## API-ключи

| Правило                                                      | Где обеспечивается                                                                       |
| ------------------------------------------------------------ | ---------------------------------------------------------------------------------------- |
| Ключи лежат в `chrome.storage`, при желании только на сессию | `core/ai/keyStore.ts`                                                                    |
| В IndexedDB ключи не пишутся                                 | больше их никто не пишет                                                                 |
| В экспорт ключи не попадают                                  | `database/transfer.ts` читает только таблицы БД                                          |
| В логи ключи не попадают                                     | `utils/logger.ts` маскирует `key`/`token`/`secret`/`authorization` и шаблоны вида `sk-…` |
| Вне service worker ключи не читаются                         | юнит-тест грепает `src/content`, `src/sidepanel`, `src/popup` на `getApiKey(`            |
| На сайт вакансий ключи не уходят                             | провайдеры вызываются только из фонового контекста                                       |

У провайдера может быть несколько ключей (рабочий и личный, разные проекты и
лимиты): они хранятся списком, активный выбирается на странице настроек, а
`getApiKey` отдаёт секрет активной записи. Ключи, сохранённые прежней версией по
одному на провайдера, поднимаются в список при первом чтении.

Страница настроек умеет _записать_ ключ и переключить активный, но не прочитать
секрет обратно: `listApiKeys` отдаёт только название и маску вида «sk-…f8Ab».

## Разрешения

При установке запрашивается минимум: `storage`, `unlimitedStorage`, `sidePanel`,
`activeTab`, `scripting`, `tabs`, `notifications`.

**Доступ к сайтам при установке не запрашивается вовсе.** Он выдаётся по одному
origin через `chrome.permissions.request()` из пользовательского жеста в панели
или попапе и отзывается в настройках. Content-скрипт внедряется через
`chrome.scripting.executeScript` только после этого.

## Правило отправки

Инвариант ровно один и он про действие, а не про запись в базе: **кнопку
«Отправить» нажимает человек**. JobPilot не отправляет форму никогда.

Что это обеспечивает:

1. `settingsSchema.automation.requireConfirmationBeforeSubmit` — это
   `z.literal(true)`, а `coerceInvariants()` восстанавливает его при каждом чтении
   и записи. Флаг запрещает расширению выполнять отправку.
2. Филлер не нажимает кнопки и не вызывает `form.submit()` (см. ниже).
3. В `submitted` заявка попадает двумя явно разными путями, и оба означают
   «человек отправил сам»:
   - `markSubmitted(id, confirmedByUser)` — галочка на экране проверки; бросает
     исключение, если `confirmedByUser` не true;
   - `markSubmittedAutomatically(id, evidence)` — наблюдение за реальным
     событием `submit`, которое инициировал пользователь на сайте. Ставит
     `submissionSource: 'auto'`, пишет событие в журнал заявки и включается
     настройкой `automation.autoMarkSubmitted`.

Разница между путями сохраняется в данных, а не теряется: автоматическую отметку
интерфейс подписывает как автоматическую и даёт откатить
(`revertAutoSubmission`), подтверждённую человеком — нет.

Филлер не нажимает кнопки отправки и не вызывает `form.submit()` или
`form.requestSubmit()` — это тоже проверяется тестом безопасности.

Автоматика только наблюдает: `content/tracking.ts` слушает событие `submit`,
которое инициировал пользователь, и ищет на странице надписи вида «отклик
отправлен». Она не может создать отправку — лишь заметить уже случившуюся.
Ложное срабатывание поправимо: запись журнала удаляется, отметка заявки
откатывается, обе функции выключаются в настройках.

## Границы content-скрипта

Content-скрипт может: читать DOM, сообщать о найденных полях, записывать
значения в поля, которые одобрил пользователь, сообщать о замеченной отправке и
рисовать собственные метки. Он не может: делать сетевые запросы, читать
хранилище, видеть ключ или отправлять форму. Своей базы у него нет — IndexedDB на
странице принадлежит сайту, поэтому за данными он всегда ходит в воркер
сообщением.

Внедряется он двумя путями и защищён от повторной регистрации:

- по требованию — `chrome.scripting.executeScript`, когда панель что-то просит;
- постоянно — `chrome.scripting.registerContentScripts` (`background/contentScripts.ts`)
  и только для тех origin, которым пользователь выдал доступ. Регистрация нужна
  пассивным функциям (журнал откликов, метки) и снимается, как только обе
  выключены в настройках. В манифесте `content_scripts` по-прежнему нет.

## Зависимости

В рантайме используются React, Zustand, Dexie, Zod и pdf.js. Нет ни аналитики,
ни SDK для отчётов об ошибках, ни ресурсов с CDN — всё собирается в бандл.

### pdf.js и динамический код

pdf.js — единственная библиотека в сборке, где есть `new Function`. Это два
места: проба `new Function("")` внутри try/catch (так библиотека узнаёт,
разрешён ли eval) и компилятор PostScript-функций, закрытый флагом
`isEvalSupported`. Под нашим CSP проба всегда возвращает false, поэтому
компилятор не запускается; вдобавок мы передаём `isEvalSupported: false` при
открытии документа.

Тест `packaging.spec.ts` закрепляет это: в наших бандлах `new Function` и `eval`
запрещены полностью, а в вендорном чанке допускается только описанная пара мест
при наличии флага. Если новая версия pdf.js принесёт другой динамический код,
тест упадёт.

PDF разбирается локально в браузере: файл никуда не отправляется, и текст
резюме уходит AI-провайдеру только когда пользователь сам нажимает «Подогнать
через AI».
